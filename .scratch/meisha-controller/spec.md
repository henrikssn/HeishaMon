# Meisha On-Device Heat Pump Controller Specification

Status: ready-for-agent

## Problem Statement

The Panasonic Aquarea M-series heat pump ("Meisha") is currently controlled by a set of Home Assistant automations, template sensors, statistics helpers, utility meters, and a PID integration, while the ESP32-S3 board running HeishaMon acts solely as a dumb serial-to-MQTT proxy. If Home Assistant crashes, restarts, or loses network/MQTT connectivity, the heat pump no longer receives **Heating Day** start commands, **Bonusgrad**/**Malusgrad** modulation adjustments, **Night Mode** budget cutoffs, domestic hot water (DHW) schedules, or evaporator-icing protection (**Quiet Mode** adjustments), risking loss of heating and hot water or inefficient short-cycling.

At the same time, replacing the entire HeishaMon firmware stack with ESPHome in one leap carries migration risk for existing Home Assistant dashboards, long-term sensor history, and over-the-air (OTA) recoverability, while HeishaMon's built-in Rules VM is too constrained to host the stateful control algorithm, accept dynamic parameters over MQTT, or persist state across reboots without wearing out flash memory.

## Solution

Embed a native C++ controller module directly inside a fork of the HeishaMon firmware on the ESP32-S3 so that all control-critical heating, DHW, cooling, and evaporator-protection logic executes autonomously on the board while preserving 100% compatibility with existing HeishaMon MQTT telemetry topics, 1-Wire sensors, Web UI OTA updates, and the Home Assistant integration.

The on-device controller exposes the five active user-tunable parameters (**Room Target**, heating curve start, heating curve angle, heating start hour, and cooling mode) plus a controller operating mode selector (`Off`, **Shadow Mode**, `Active`) and all derived internal control sensors to Home Assistant via MQTT Auto-Discovery using the `meisha_esp_` identifier prefix during validation. In **Shadow Mode**, the controller computes all rolling averages, targets, budgets, and proposed commands and publishes them to MQTT without actuating the heat pump, allowing side-by-side verification against the existing Home Assistant automations before switching to `Active` mode and retiring the Home Assistant control automations. High-frequency state and rolling-average ring buffers are kept in CRC32-guarded non-initialized RTC SRAM (surviving OTA updates and software reboots with zero flash writes), backed by a compact 32-byte wear-leveled NVS flash checkpoint written only on daily reset and once every two hours while the heat pump is running.

## Implementation Decisions

- **Firmware Architecture & Crash-Loop Safeguard (ADR-0001)**:
  - The controller will be implemented as a native C++ module (`MeishaController`) inside a fork of `heishamon/HeishaMon` targeting the ESP32-S3 (`HeishaMon Large`).
  - `HeishaMon.ino` will invoke four lifecycle hooks: initialization in `setup()`, periodic execution in `loop()`, MQTT subscription/discovery registration in `mqtt_reconnect()`, and incoming MQTT message handling in `mqtt_callback()`.
  - To keep the implementation simple and direct, the controller module may call HeishaMon and Arduino primitives (`getDataValue`, `send_heatpump_command`, `mqtt_client`, `Preferences`, `millis`, `time`/`localtime`) directly rather than introducing an abstract adapter layer. When later migrating to ESPHome, this C++ module will be forked and its hardware/MQTT/NVS calls replaced with ESPHome equivalents.
  - **Crash-Loop Anti-Brick Safeguard**: Instead of HeishaMon's default `/rules.txt` check (which disables rules on the very first brownout or watchdog reset), `MeishaController` tracks abnormal resets (`ESP_RST_PANIC`, `ESP_RST_INT_WDT`, `ESP_RST_TASK_WDT`, `ESP_RST_WDT`) in `RTC_NOINIT_ATTR` SRAM. If more than 3 crashes occur within a 5-minute (`300 s`) window (with the crash counter cleared once continuous uptime reaches 5 minutes, `millis() >= 300000`), `MeishaController` forces `control_mode` to `Off` during `setup()`, writes `Off` to NVS, and publishes `Off` to MQTT, skipping controller loop execution so the device cannot brick and remains reachable via Web UI OTA.

- **Operating Modes (`Off` / `Shadow` / `Active`) & HA Notification**:
  - The controller exposes a mode select entity (`Off`, `Shadow`, `Active`, defaulting to `Shadow` on first flash and persisted in NVS).
  - In `Off` mode, the controller evaluates no control actions (and when tripped by the crash-loop safeguard, skips loop processing entirely to guarantee stability), while publishing its `Off` state to MQTT.
  - In **Shadow Mode**, the controller runs the full state machine and publishes all derived sensors plus `last_action_reason` / proposed command telemetry to MQTT, but suppresses calls to `send_heatpump_command()` (and does not mutate its internal `change_lock` or pending command queue in a way that masks real heat pump state transitions).
  - In `Active` mode, all heat pump commands are queued via `send_heatpump_command()`.
  - A Home Assistant automation monitors the controller's mode entity (`select.meisha_esp_control_mode` / `select.meisha_control_mode`) and dispatches a `notify.all_devices` alert whenever its state becomes `Off`.

- **Non-Blocking Command Sequencing**:
  - Several automations require a 10-second delay between setting an operating mode (or turning the heat pump on) and issuing the follow-up command (`Day Mode #1` 10s wait after reset, `Turn Off Heat` 10s wait after setting `Heat only`, `DHW start` 10s wait after turning HP on before setting `DHW only`, `DHW end` in cooling season 10s wait after setting `Cool only` before conditional turn-off, `Cooling Turn On` 10s wait after setting `Cool only` before turning HP on).
  - All such multi-step sequences must be implemented as non-blocking timestamped state steps inside the controller's periodic loop using `millis()`, never `delay(10000)`, so HeishaMon's UART polling, web server, and MQTT loop are never blocked.

- **Two-Tier State Persistence (ADR-0002)**:
  - **Tier 1 (`RTC_NOINIT_ATTR` SRAM)**: A stationary struct in `RTC_NOINIT_ATTR` memory holds the full rolling-average ring buffers (`ambient_24h` 1-minute samples or 1440-slot / downsampled ring buffer, `ambient_1h` 60×1-minute samples, `room_temp_6h` 360×1-minute samples), `room_temp_snapshot`, `degree_hours_day`, `dhw_time`, `pid_output`, `power_target`, `change_lock` deadline, duration timer start timestamps, crash-loop counter/timestamps, and a 32-bit CRC32 checksum. On every soft reboot, OTA update, or watchdog reset where the CRC32 is valid, the controller resumes immediately with zero sample loss and zero flash writes.
  - **Tier 2 (ESP32 NVS Flash via `Preferences`)**:
    - User tunables (`room_target`, `heating_curve_start`, `heating_curve_angle`, `heating_start_hour`, `cooling_mode`, and `control_mode`) are stored in NVS only when modified via MQTT (and only when the new value differs from the current value), or when the crash-loop safeguard forces `control_mode` to `Off`.
    - Operational state is checkpointed to NVS as a fixed **32-byte scalar summary struct** (`ambient_24h_mean`, `ambient_1h_mean`, `room_temp_6h_mean`, `room_temp_snapshot`, `degree_hours_day`, `dhw_time`, `pid_output`, `saved_at_epoch`) only at the daily `heating_start_hour:00` reset and once every 2 hours while the heat pump is running (`Heatpump_State == 1`).
    - On a cold boot where `RTC_NOINIT_ATTR` CRC32 is invalid:
      - If `saved_at_epoch` in NVS is valid and `< 6 hours` old, the ring buffers are pre-filled with `ambient_24h_mean`, `ambient_1h_mean`, and `room_temp_6h_mean`, and `pid_output` (plus `degree_hours_day`, `dhw_time`, and `room_temp_snapshot` if still within the same **Heating Day**) are restored.
      - If `saved_at_epoch` is missing or `>= 6 hours` old, `pid_output` and tunables are restored from NVS, and the ring buffers (plus `room_temp_snapshot`) are seeded from the first valid live heat pump readings (`Outside_Temp` and `Room_Thermostat_Temp`, falling back to `room_target` if `Room_Thermostat_Temp` is unavailable).

- **Inputs, Tunables & Dropped Legacy Dependencies**:
  - **Heat Pump Telemetry Inputs (read from HeishaMon decoded state)**: `Heatpump_State` (`TOP0`), `Pump_Flow` (`TOP1`), `Main_Inlet_Temp` (`TOP5`), `Main_Outlet_Temp` (`TOP6`), `Main_Target_Temp` (`TOP7`), `Compressor_Freq` (`TOP8`), `DHW_Target_Temp` (`TOP9`), `DHW_Temp` (`TOP10`), `Outside_Temp` (`TOP14`), `Operating_Mode_State` (`TOP4`), `ThreeWay_Valve_State` (`TOP20`), `Outside_Pipe_Temp` (`TOP21`), `Defrosting_State` (`TOP26`), `Z1_Heat_Request_Temp` (`TOP27`), `Room_Thermostat_Temp` (`TOP33`), `Z1_Temp` (`TOP34`), and `Quiet_Mode_Level` (`TOP18`). Wait until the first valid `0x10` heat pump frame (`actData[0] == 0x71`) has been decoded before running control ticks.
  - **5 Active User Tunables**:
    1. `room_target`: `18.0–25.0 °C`, step `0.5 °C` (or `0.1 °C`), default `23.0 °C`
    2. `heating_curve_start`: `12.0–20.0 °C`, step `1.0 °C`, default `14.0 °C`
    3. `heating_curve_angle`: `0.2–1.5`, step `0.1`, default `0.8`
    4. `heating_start_hour`: `0–23`, step `1`, default `9`
    5. `cooling_mode`: boolean switch (`off`/`on`), default `off`
  - **Dropped External & Legacy Entities**: `weather_forecast_home_temperature_24h` and `sensor.garage_dew_point` are dropped. Disabled automations (`day mode #2`, `day mode #3`, `bonusgrad power`, `DHW set heating target temp`), dead variables (`t_d`, `power_base`, `extra`), and unused helpers (`fixed_target`, `power_max_outlet_temp`, `high_power_override`) are omitted.

- **Control Formulas & State Machine Rules**:
  - **Compressor Running Binary State**: Hysteresis threshold on `Compressor_Freq` with upper threshold `10.0 Hz` and hysteresis `2.0 Hz` (turns `on` when `Compressor_Freq > 12.0 Hz` or `> 10.0 Hz` per HA threshold semantics: in Home Assistant `threshold` integration with `upper: 10.0, hysteresis: 2.0`, it turns `on` above `10.0 + 2.0 = 12.0 Hz` and `off` below `10.0 - 2.0 = 8.0 Hz`).
  - **Curve Target**:
    - `heating_curve_ambient = round2(room_target + (heating_curve_start - ambient_24h) * heating_curve_angle)`
    - `room_offset = clamp(-2.0, room_target - room_temp_snapshot, +2.0)`
    - `curve_target = round2(heating_curve_ambient + room_offset * heating_curve_angle)`
  - **Degree-Hour Budget & Progress**:
    - `room_delta = (pump_flow > 0 && valve == Room) ? (main_outlet_temp - room_target) : 0.0`
    - `degree_hours_day`: trapezoidal/step integral of `room_delta` over time in hours (`Kh`), reset to `0.0` at `heating_start_hour:00`.
    - `degree_hours_target = 24.0 * (curve_target - room_target)`
  - **I-Only PID & Power Target**:
    - `curve_error = (pump_flow > 0 && valve == Room) ? (curve_target - main_outlet_temp) : 0.0`
    - Sampled every `10 s`: `pid_error = 0.0 - curve_error = main_outlet_temp - curve_target`; `pid_output = clamp(pid_output + 5e-5 * 10.0 * pid_error, -1.0, +1.0)`.
    - `raw_power_target = max(27.0, curve_target - pid_output)`
    - `power_target = clamp(round(raw_power_target - 0.1), prev_power_target, round(raw_power_target + 0.1))` (integer `°C`).
  - **Time-Based Helpers**:
    - `dhw_time`: cumulative hours `valve == Tank` since `heating_start_hour:00` (reset at `heating_start_hour:00`).
    - `hours_target = clamp(0.0, (curve_target - room_target) / (30.0 - room_target) * 24.0, 24.0)` (guarded against `room_target == 30.0`).
    - `hours_time_left = max(0.0, min(24.0, hours_target + dhw_time) - hours_elapsed_since_start_hour)`.
  - **Heating Automations (all gated on `cooling_mode == off`)**:
    - `Day Mode #1`: At `local_hour == heating_start_hour && local_minute == 0` (once per day): snapshot `room_temp_snapshot = round1(room_temp_6h)`, reset `degree_hours_day = 0` and `dhw_time = 0`, recompute targets, and if `hours_time_left > 1.0`: ensure operating mode is `Heat only` (when `valve != Tank` and mode != `DHW only`), turn HP on, and if `int(heat_pump_setpoint) < max(27, power_target)` set **Heat Pump Setpoint** to `max(27, power_target)`.
    - **Bonusgrad Curve**: Requires `cooling_mode == off`, `valve == Room` for `>= 10 min`, `compressor_running == on` for `>= 5 min`, `int(main_outlet_temp) + 1 > main_target_temp`, `degree_hours_day * 1.05 < degree_hours_target`, `int(heat_pump_setpoint) < power_target`, and `now >= change_lock`. Sets **Heat Pump Setpoint** to `max(int(heat_pump_setpoint) + 1, int(z1_temp) + 1)` and `change_lock = now + 30 min`.
    - **Malusgrad**: Requires `cooling_mode == off`, `valve == Room` for `>= 10 min`, `compressor_running == on` for `>= 5 min`, `int(main_outlet_temp) - 1 < main_target_temp`, `main_target_temp > power_target`, `int(heat_pump_setpoint) > power_target`, and `now >= change_lock`. Sets **Heat Pump Setpoint** to `max(min(int(heat_pump_setpoint) - 1, int(z1_temp) - 1), power_target)` and `change_lock = now + 20 min`.
    - **Bonusgrad High-Temp (Anti-Overshoot)**: Requires `cooling_mode == off`, `valve == Room`, `compressor_running == on`, `degree_hours_day < degree_hours_target`, and `z1_temp >= int(heat_pump_setpoint) + 3` continuously for `1 min` (and may fire a second time if `z1_temp >= int(heat_pump_setpoint) + 3` still holds continuously for `1 min` after the first increment, matching the 1-min + 2-min trigger pair). Ignores `change_lock`. Increments **Heat Pump Setpoint** by `+1` and sets `change_lock = now + 15 min`.
    - **Night Mode**: When `cooling_mode == off`, HP is on, `degree_hours_day > degree_hours_target`, `((heating_start_hour - local_hour + 24) % 24) not in {1, 2}`, and `heat_pump_setpoint != 25`, sets **Heat Pump Setpoint** to `25 °C`.
    - **Turn Off (Heat Mode Only)**: When `cooling_mode == off`, HP is on, `valve == Room`, operating mode != `DHW only`, and `heat_pump_setpoint < 25.1` continuously for `4 hours`: sets operating mode to `Heat only`, waits `10 s` non-blockingly, and turns HP off (re-verifying `valve == Room` and mode != `DHW only` before turning off).
  - **Domestic Hot Water (DHW)**:
    - `DHW Start`: Triggers at `14:00` or when `dhw_temp < 38.0 °C` continuously for `1 min`. Requires `valve != Tank` and `dhw_temp < 45.0 °C`. If HP is off, turns HP on; waits `10 s` non-blockingly; sets operating mode to `DHW only`.
    - `DHW End`: Triggers when operating mode is `DHW only` and either (`valve` transitioned `Tank -> Room` and remained `Room` for `15 min`) or (`compressor_running == off` continuously for `15 min`). If `cooling_mode == on`, sets operating mode to `Cool only`, waits `10 s` non-blockingly, and if `ambient_24h < 22.0 °C` turns HP off. If `cooling_mode == off`, sets operating mode to `Heat only` and if `hours_time_left < 0.1` turns HP off.
  - **Cooling Season (gated on `cooling_mode == on`)**:
    - `Cool Turn On`: At `08:00`, if `cooling_mode == on` and `ambient_24h > 24.0 °C`: sets operating mode to `Cool only`, waits `10 s` non-blockingly, and turns HP on.
    - `Cool Turn Off`: At `20:00` or when `ambient_24h < 22.0 °C` continuously for `1 hour`, if `cooling_mode == on` and HP is on: turns HP off.
  - **Quiet Mode / Evaporator Protection (`FM off` / `FM on`)**:
    - `pipe_ambient_delta = outside_temp - outside_pipe_temp`.
    - `FM Off`: When `quiet_mode_level != 0` and (`pipe_ambient_delta > 4.0` or (`pipe_ambient_delta > 3.0` and `outside_temp < 1.1`)) and any trigger duration holds (`compressor_freq > 25.0` for `1 min`, `pipe_ambient_delta > 4.0` for `5 min`, `pipe_ambient_delta > 3.0` for `5 min`, or `outside_temp < 1.1` for `5 min`), sets Quiet Mode to `0` (`Off`).
    - `FM On`: When `quiet_mode_level == 0`, `1.0 < compressor_freq < 23.5`, `defrosting_state == 0` continuously for `2 hours`, `pipe_ambient_delta < 3.1`, (`pipe_ambient_delta < 2.1` or `outside_temp > 1.0`), and either (`1.0 < compressor_freq < 23.5` for `1 min`) or (`pipe_ambient_delta < 4.0` transition), sets Quiet Mode to `1`.

- **MQTT Auto-Discovery & Entity Prefix**:
  - All controller-published entities use a compile-time configurable prefix defaulting to `meisha_esp_` (e.g., `number.meisha_esp_room_target`, `sensor.meisha_esp_heating_curve_target`, `select.meisha_esp_control_mode`) so they coexist alongside the legacy `meisha_` Home Assistant helpers during **Shadow Mode** validation, and can be switched to `meisha_` once the legacy helpers are retired.

## Testing Decisions

- **What Makes a Good Test**:
  - Tests must verify observable external behavior—specifically the heat pump commands emitted (`send_heatpump_command`), the MQTT states/discovery payloads published (`mqtt_client.publish`), and the NVS checkpoints written (`Preferences`) in response to sequences of simulated heat pump telemetry frames, incoming MQTT tunable changes, simulated wall-clock/monotonic time advances, and simulated reboots—rather than asserting on private internal helper functions.
- **Modules to Test**:
  - The native C++ controller module (`MeishaController`) compiled on the Linux host against lightweight C++ test doubles/mocks for the HeishaMon/Arduino externs (`getDataValue`, `send_heatpump_command`, `mqtt_client`, `Preferences`, `millis`, `localtime`, `esp_reset_reason`, and `RTC_NOINIT_ATTR` memory).
  - Test scenarios will cover:
    1. Cold-start seeding vs. warm reboot (`RTC_NOINIT_ATTR` CRC32 valid vs. `< 6h` NVS checkpoint vs. `>= 6h` stale NVS checkpoint) and NVS write-frequency throttling (verifying flash writes only occur on tunable change, daily reset, and 2-hour active intervals).
    2. Crash-loop anti-brick safeguard: verifying that 1–3 crash resets (`ESP_RST_PANIC` / `ESP_RST_WDT`) within 5 minutes preserve the active `control_mode` and reset the crash counter after 5 minutes of uptime, whereas a 4th crash reset within 5 minutes forces `control_mode` to `Off` in NVS and MQTT and disables controller tick execution.
    3. Rolling-average calculation (`ambient_1h`, `ambient_24h`, `room_temp_6h`), **Heating Day** reset at `heating_start_hour:00`, `0.1 °C` room snapshot, **Curve Target**, 10-second I-only PID integration with `[-1, +1]` clamping, and **Power Target** `±0.1 K` hysteresis.
    4. **Degree-Hours Day** integration (only when `pump_flow > 0` and `valve == Room`), **Bonusgrad** curve ramp (+30m **Change Lock** enforcement), **Malusgrad** ramp (+20m **Change Lock** enforcement), and **Bonusgrad** high-temp anti-overshoot (1m/2m triggers bypassing **Change Lock**).
    5. **Night Mode** transition (`25 °C` when **Degree-Hours Day** exceeds **Degree-Hour Budget** outside the 2h pre-start blackout window) and 4-hour delayed shutoff (with 10s non-blocking mode change and DHW safety guard).
    6. `DHW start` (`14:00` and `< 38 °C` for 1m) and `DHW end` (15m valve `Room` or 15m compressor off, seasonal mode restoration, and `dhw_time` credit).
    7. Cooling season `08:00` start (`ambient_24h > 24 °C`) and `20:00` / `< 22 °C` for 1h shutoff, plus heating automation suppression when `cooling_mode` is `on`.
    8. Quiet Mode evaporator protection (`FM off` and `FM on` including the 2-hour post-defrost guard).
    9. `Off` vs. **Shadow Mode** vs. `Active` mode command gating.
- **Prior Art**:
  - HeishaMon's own host-side C++ test harness (`Examples/Rules/harness/` in `heishamon/HeishaMon`), which compiles firmware logic with `g++` on Linux by providing stub implementations of Arduino/ESP32 globals and heat pump topic arrays.

## Out of Scope

- Porting the Home Assistant monitoring, energy/COP calculation chain, utility-meter tariff selects (`Heat`/`DHW`/`Cool`), defrost counter, or low-water-pressure phone notifications (§8 of [`/config/docs/meisha-heat-pump-control.md`](file:///config/docs/meisha-heat-pump-control.md)), which remain in Home Assistant (alongside the new `MeishaController` `Off`-state notification).
- Porting disabled legacy automations (`Meisha day mode #2`, `Meisha day mode #3`, `Meisha bonusgrad power`, `Meisha DHW set heating target temp`) and unused helpers (`meisha_fixed_target`, `meisha_heating_power_max_outlet_temp`, `meisha_heating_high_power_override`).
- Integrating external Home Assistant weather forecast (`weather_forecast_home_temperature_24h`) or garage dew point (`sensor.garage_dew_point`) sensors (a local garage humidity sensor connected directly to the ESP32 may be added in a future effort).
- Migrating the firmware stack to ESPHome (deferred to a future phase once the native C++ controller has been validated in HeishaMon).
